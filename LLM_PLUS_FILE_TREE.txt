================================================================================
*** CORE INNOVATION: THE TRACTATUS TREE MEMORY SYSTEM ***
================================================================================

This is the feature that effectively ENLARGES the model's context window
beyond its native limit. It is the system that should be ported to other apps.

WHAT IT IS
----------
A per-project Tractatus tree is a flat JSON object stored in JSONB:

    {
      "1.0":   "ASSERTS: User is litigating UBS arbitration over advisor fees.",
      "1.1":   "DOCUMENT: UBS_settlement_offer.pdf, dated 2024-03-15.",
      "1.1.1": "ASSERTS: Settlement offered $42,000 against $78,000 claim.",
      "1.2":   "REJECTS: User declines mediation.",
      "2.0":   "OPEN: Statute of limitations question for 2019 transfers.",
      "2.0.1": "QUESTION: Does NY CPLR 213(2) or FINRA 6-year rule control?",
      "3.0":   "RESOLVED: Discovery deadline set for 2025-09-01."
    }

Keys are Wittgenstein-style numbered outlines ("1.0", "1.1", "1.1.1", "2.0").
Values are tagged summaries using a fixed vocabulary:

    ASSERTS:    a positive claim now in the record
    REJECTS:    a claim explicitly denied
    ASSUMES:    a working assumption not yet verified
    OPEN:       an unresolved question or thread
    RESOLVED:   a previously open item now closed
    DOCUMENT:   a reference to an uploaded source
    QUESTION:   a question the project is trying to answer

WHY IT EXPANDS THE CONTEXT WINDOW
---------------------------------
Every chat exchange is summarised into 1-5 new nodes appended to the tree.
On the NEXT message, the tree (not the raw transcript) is injected into the
system prompt. So a 200-message conversation that would never fit in a
200K-token window is represented by ~200 nodes (~10-15 KB), and the model
behaves as if it remembers everything.

The tree is rendered in a compact `key: value\n` format, NOT JSON, to save
tokens — 30-40% smaller than JSON.stringify with no semantic loss.

THREE LAYERS OF CONTEXT FED TO EVERY CHAT REQUEST
-------------------------------------------------
    1. Tiered tractatus memory   <-- the "long memory"     (~15K char budget)
    2. Last 16 messages of CURRENT session                 (~8K chars each, capped)
    3. 6 messages x 400 chars from OTHER sessions          (~10K total, cross-session)

Total system+context cap: ~100K chars. Logged to console for monitoring.


================================================================================
RECURSIVE COMPRESSION - THE TIERED MEMORY HIERARCHY
================================================================================

When a project's Tier 1 tree reaches 200 nodes, it is automatically compressed
into a higher-tier summary. This is what allows the system to retain memory
of arbitrarily long projects.

TIER STRUCTURE
--------------
    Tier 1   "recent, high resolution"        live tree, current project row
    Tier 2   "summary, medium resolution"     compression of old Tier 1 nodes
    Tier 3   "archive, lower resolution"      compression of Tier 2 (rare)
    Tier 4+  "deep archive"                   recursive, theoretically unbounded

Each tier is stored as its own row in `projects` with `tractatus_tier > 1`
and `parent_project_id` pointing back at the live project. These summary
projects are HIDDEN from the main project list (the SELECT in /api/projects
filters `tractatus_tier = 1 OR IS NULL`).

PER-TIER CHARACTER BUDGETS injected into the system prompt:
    Tier 1:  8,000 chars
    Tier 2:  4,000 chars
    Tier 3+: 2,000 chars
    Total:  15,000 chars

COMPRESSION TRIGGER & ALGORITHM (server/index.js compressTractatusTier)
-----------------------------------------------------------------------
Runs INSIDE a database transaction (BEGIN/COMMIT/ROLLBACK).

Step 1  Snapshot the full pre-compression tree into tractatus_archive
        with its tier number and node count. (PRESERVES history.)

Step 2  Send the full tree to Claude with a strict prompt:
          - Reduce to roughly 50-80 nodes
          - PRESERVE adverse findings, defeats, dates, dollar amounts EXACTLY
          - Never reframe a defeat as an "opportunity" (anti-sycophancy)
          - Use the same tag vocabulary
          - Return ONLY valid JSON
        max_tokens = 8192. Bare-string + JSON-fence cleanup, then JSON.parse.

Step 3  Either MERGE the new summary into an existing Tier (currentTier+1)
        summary project, OR CREATE a new summary project if none exists.

Step 4  Trim the live Tier 1 tree: keep the 30 most recent nodes
        (no cliff — the model still has very-recent detail at high resolution).
        UPDATE projects SET tractatus_tree = kept, compression_count += 1.

Step 5  If the merged Tier 2 itself now has >= 200 nodes, RECURSE into the
        same function with the next tier up. This is how Tier 3+ are born.

The chat-side helper loadTieredMemory(projectId) walks
parent_project_id links breadth-first and assembles all tiers in
ascending order for injection into buildSystemPrompt().

================================================================================
ANTI-SYCOPHANCY: PROTECTED ACROSS THE WHOLE MEMORY PIPELINE
================================================================================

A critical design requirement is that NEGATIVE FINDINGS survive the full
memory lifecycle without being softened into "opportunities" or "lessons."

Three places enforce this with matching language:

  1. buildSystemPrompt()           "NEVER reframe a defeat as a victory"
                                   "preserve negative findings with the same
                                    fidelity as positive ones"

  2. /api/tractatus/update prompt  "If the user lost a motion, record
                                    'ASSERTS: Motion denied' - not
                                    'ASSERTS: Denial creates strategic
                                    opportunity.'"

  3. compressTractatusTier prompt  "Preserve adverse findings, defeats,
                                    setbacks, and losses with FULL fidelity
                                    and equal weight to positive developments.
                                    Do NOT soften bad news during compression."

Stance toggle is orthogonal to truthfulness: Agreeable steel-mans the user's
position, Strongly Critical steel-mans the contrary, but ALL FOUR stances are
bound by the universal rules and CANNOT invent supporting or counter-evidence.

================================================================================
THE THREE-PASS COHERENCE ENGINE (LONG-FORM GENERATION)
================================================================================

For documents up to 150,000 words. Lives at POST /api/coherence.
Streams progress to a "paper popup" on the frontend.

PASS 1 - OUTLINE
  - Claude produces a numbered section outline keyed to the user's instructions
  - Section sizes scale with target length:
      < 10K words   -> 1500 words/section
      10K - 20K     -> 2000 words/section
      20K+          -> 3000 words/section
  - extractSectionOutline() parses the outline into structured sections

PASS 2 - SECTION WRITING WITH CONTINUATION
  - For each section:
      - Source material is keyword-matched against selected docs (50K char budget)
        - NOT generic truncation; grep-style relevance
      - If "Fetch Scholarly Sources" is checked:
          - 3-5 search queries generated per section
          - Semantic Scholar + OpenAlex + CrossRef + PubMed hit IN PARALLEL
          - Results deduplicated by title, formatted with author/year/abstract/DOI
          - Injected into section prompt with citation instructions
          - Auto-rephrase + retry if zero results
      - streamClaudeWithContinuation chains up to 6 calls per section
      - Each token streamed live into the paper popup
  - 15-second mandatory pause between sections (rate-limit protection)

PASS 3 - GLOBAL STITCH & REPAIR
  - Final coherence pass over the assembled document
  - User can "Revise" the completed output without restarting

DB-BACKED for reliability:
  - document_jobs row tracks the run
  - document_chunks rows store each section's input/output/delta
  - The engine queries the DB every chunk - never trusts in-memory state


================================================================================
USER ANALYTICS - CROSS-PROJECT PROFILE TREE
================================================================================

A SECOND tractatus tree, scoped per USER instead of per project. Builds
incrementally by analyzing all project trees + the latest conversation.

Profile tree categories:
    1.x  Topics
    2.x  Conversational Style
    3.x  Writing Patterns
    4.x  Cognitive Patterns
    5.x  Emotional Patterns
    6.x  Evolution

Built by:
    updateUserProfileTree()   fires every 5th chat exchange in background
    /api/profile/generate     produces a clinical 800-1500 word profile via SSE
                              with a "Changes Since Last Profile" diff section

Snapshots saved to profile_snapshots for longitudinal tracking.


================================================================================
SYSTEM DIAGNOSTIC - 5-PHASE SELF-CHECK
================================================================================

POST /api/diagnostic/run (SSE). Streams PASS/FAIL + timing for each step.

  1. ENVIRONMENT       6 env vars (4 LLM keys + Vision + session secret)
  2. DATABASE          ping + verify all 10 required tables
  3. EXTERNAL LLM APIS 1-token ping to Anthropic / OpenAI / DeepSeek / xAI
                       HTTP 429 / 5xx are reported as "upstream — key OK"
  4. FUNCTIONAL CRUD   creates throwaway project + session + global doc +
                       reminder; exercises ownership verification, tractatus
                       tree round-trip, staleness query, system-prompt builder
  5. CLEANUP           deletes everything created during the test


================================================================================
PORTING THE TRACTATUS SYSTEM TO ANOTHER APP - CHECKLIST
================================================================================

This is the minimum surface area you need to replicate to get the
"enlarged context window" behavior in any chat app.

1. DATABASE
   - Add a JSONB column `tractatus_tree` to your project/conversation table
   - Add INTEGER `tractatus_tier DEFAULT 1`
   - Add UUID `parent_project_id` FK back to the same table
   - Add TIMESTAMPTZ `last_tree_update`
   - Add INTEGER `compression_count DEFAULT 0`
   - Create `tractatus_archive` table: (project_id, tier, tree JSONB, node_count, created_at)

2. PROMPT-BUILDER MODULE
   - compactTreeString(tree)               // render as `key: value\n` not JSON
   - buildSystemPrompt(tree, tieredMemory) // inject all tiers under labeled
                                           // headings with per-tier char budgets
                                           // (8K / 4K / 2K, total 15K)
   - loadTieredMemory(projectId)           // BFS walk parent_project_id chain

3. UPDATE PIPELINE  (run AFTER each assistant response)
   - tryParseTractatusJSON(text)           // tolerant JSON parser w/ fence cleanup
   - POST /tractatus/update endpoint
   - Stream the LLM call to the client so the user sees the tree forming
   - On parse fail, retry once with a simpler prompt; skip if both fail
   - Object.assign(existingTree, newTree) and UPDATE the row
   - Trigger compression when nodeCount >= 200

4. COMPRESSION  (transactional)
   - compressTractatusTier(projectId, fullTree, nodeCount, sendFn, userId)
   - INSERT pre-compression snapshot into tractatus_archive FIRST
   - Send tree to LLM with strict JSON-only system prompt and explicit
     anti-sycophancy rules (preserve defeats / dates / amounts exactly)
   - max_tokens 8192; reduce to 50-80 nodes
   - Either MERGE into existing tier+1 summary row OR INSERT a new one
     (same table, different `tractatus_tier` value, parent_project_id set)
   - Trim the live tree to its 30 most recent nodes
   - Increment compression_count
   - Recurse if the merged higher tier itself crosses the threshold

5. ANTI-SYCOPHANCY  (must appear in THREE places, identically worded)
   - buildSystemPrompt
   - /tractatus/update prompt
   - compressTractatusTier prompt
   This is what stops the model from softening defeats during memory
   updates and compressions, which is otherwise a silent failure mode.

6. STALENESS DETECTION
   - GET /projects/:id/staleness returns daysSinceUpdate + severity
     (mild >= 3 days/2 compressions; warning >= 7/3; critical >= 14/5)
   - When stale, inject anti-hallucination clauses into system prompt:
     "ALWAYS qualify uncertain specifics", "NEVER fabricate details",
     "Recommend Audit if accuracy is critical"

7. AUDIT (FACT-CHECK)  (highly recommended companion)
